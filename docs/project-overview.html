Project Overview

Real-time fault monitoring and reporting for a simulated power-grid environment.

Purpose Fault Detection Real-Time Tasks System Flow Communication Methods Testing Modes Original Writing

Application Purpose

This application was designed to demonstrate a real-time system that monitors and reports the condition of a simulated power grid, with specific attention given to fault events.

The simulation is implemented in Wokwi. A push button represents a power-grid fault and allows fault events to be introduced during testing. When the button is pressed, the system begins the fault-handling process.

Primary goal: Detect a simulated fault quickly, classify its condition, update the system indicator, and preserve the result in the system log.

Interrupt-Driven Fault Detection

The simulated fault button is configured as a hardware interrupt. This allows the system to respond immediately when a fault occurs rather than repeatedly checking the button through periodic polling.

An interrupt-driven design allows the processor to continue performing normal work until an event requires immediate attention. When the event occurs, the interrupt service routine records and signals the fault so the appropriate processing task can respond.

Real-Time Task Structure

The application uses four periodic tasks to simulate the major responsibilities of a power-grid fault-monitoring system. The tasks are ordered according to their real-time priority.

1

Fault Monitor

Detects and monitors incoming simulated fault events. This task has the highest priority because fault recognition is the most time-sensitive system function.

2

Fault Status Classification

Examines the recorded fault timestamp and assigns a classification representing the detected system condition.

3

Update Fault Indicator

Updates the fault indicator according to the current classification and the simulated health of the power-grid system.

4

Power Grid Health Logging

Records the system condition, task activity, and fault information so the application maintains a history of its operation.

System Logic and Data Flow

The system begins by monitoring for a simulated fault event. Once the event is detected, its timestamp is recorded and passed through the classification process.

The resulting classification determines how the fault indicator represents the overall health of the system. The system condition and fault information are then logged for monitoring and record-keeping purposes.

Fault Event  →  Fault Monitoring  →  Status Classification  →  Indicator Update  →  Health Logging

ISR Communication Comparison

Another major feature of the application is the comparison between a binary semaphore and a direct task notification. Both mechanisms are used to signal a bottom-half task after the interrupt service routine detects a simulated fault.

Binary Semaphore

The binary semaphore provides a general synchronization mechanism that allows the interrupt service routine to signal a waiting task.

Direct Task Notification

The direct task notification sends the event directly to a specific task and is evaluated as a lower-overhead alternative for the fault-response path.

Measuring both methods makes it possible to determine which option provides the most effective response for this specific interrupt-driven application.

Idle and Loaded Testing

The application includes a configuration that allows the fault response to be tested with the four periodic tasks disabled or enabled.

No-Load Mode

The interrupt communication paths are measured while the processor has minimal competing work. This represents an ideal or peak-performance condition.

Loaded Mode

The four periodic application tasks are enabled while the interrupt paths are measured. This provides a more realistic test of the fault-monitoring system under active processor load.

Comparing these operating modes demonstrates how task priorities, processor load, and preemption influence the response time of the fault-handling system.

Overall Result

The completed application provides a functional demonstration of real-time fault monitoring for simulated power infrastructure.

It combines interrupt-based event detection, prioritized periodic tasks, fault classification, condition indication, system logging, and communication-latency testing.

The design offers several opportunities to test timing behavior, compare FreeRTOS communication methods, observe scheduling effects, and evaluate system performance under different processor loads.

Original Project Overview

The following is the complete original project overview as written, without shortening or restructuring.

This Application was designed to demonstrate a Real Time system to monitor and report on a simulated Power Grid. Specifically in relation to any form of fault event. This simulation is done in Wokwi using a button as the trigger for a simulated fault event. This is formulated as a hardware interrupt to avoid waiting for periodic polling.

This code operates using four tasks to simulate all aspects of a fault monitoring system. These tasks are ordered by priority: Fault Monitor, Fault Status Classification, Update Fault Indicator and finally Power Grid Health Logging.

The tasks are named to be self-explanatory, but I feel explaining the flow of logic better emphasizes the code at work. The system monitors a fault event and classifies each time stamp accordingly. There is an indicator that depends on the classification of the time stamp that will change based on the overall health of the system. This then is all logged for record keeping purposes.

Another feature of this application is to compare the efficacy of a binary semaphore and direct task notification. This was to determine the best option for our system in regards of the ISR.

This also meant implementing a toggling feature to have the system with no load and under load. This was useful for comparing a peak condition example to a more realistic variant of the system.

This application operates smoothly and allows for a litany of testing opportunities.
